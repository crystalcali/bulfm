# BULFM — LFM3 Browser RL on DGX Spark

Локальное дообучение **LiquidAI/LFM3-1.7B** управлению браузером с помощью **GRPO + LoRA**. Модель видит accessibility tree страницы, выдаёт действие BrowserGym, получает настоящую награду MiniWoB и обновляет адаптеры. Данные генерируются взаимодействием со средой: скачивать обучающий датасет не нужно.

Терминал с `/`-командами, историей и автодополнением напоминает Hermes. Дашборд показывает реальные метрики работающего процесса, обновляется каждые 2 секунды и не требует аккаунтов.

## Быстрый запуск на Spark

На Spark нужны работающий NVIDIA-драйвер (`nvidia-smi`), `git`, `curl` или `wget` и доступ к GitHub, PyPI, download.pytorch.org и Hugging Face. Предварительно ставить Python 3.12 и PyTorch не требуется: установщик найдёт подходящий Python/CUDA torch среди существующих окружений или создаст отдельную `.venv` с Python 3.12 и официальным ARM64 CUDA PyTorch `2.14.1+cu130`. После установки выполняется настоящий bf16 matmul на GPU. Системный Python и чужие окружения не изменяются.

`uv` ищется в PATH, `~/.local/bin` и `~/.cargo/bin`; при отсутствии устанавливается в `.tools/uv` без sudo и изменения профиля оболочки. Уже работающий PyTorch 2.14.1–2.15.x сохраняется, если он доступен внутри `.venv`. Пакеты другого virtualenv автоматически не наследуются: в таком случае CUDA torch устанавливается отдельно в окружение BULFM. Некорректная старая `.venv` сохраняется как `.venv.backup-*`.

```bash
git clone https://github.com/crystalcali/bulfm.git
cd bulfm
# Если CUDA torch находится в другом Python:
# export BULFM_PYTHON=/path/to/cuda/python
bash scripts/setup_spark.sh
./start.sh
```

В терминале:

```text
/doctor
/dashboard
/train configs/spark-smoke.yaml
/status
```

После успешного smoke-запуска:

```text
/train configs/spark-book-flight-parallel.yaml
```

`setup_spark.sh` устанавливает приложение, Chromium и фиксированную версию страниц MiniWoB. Первичная загрузка CUDA PyTorch и его библиотек может занимать несколько гигабайт и заметное время. `BULFM_PYTHON` — необязательный явный выбор уже работающего Python 3.12 с CUDA torch; без него действует автоматический поиск/создание окружения. Если Playwright сообщает об отсутствующих системных библиотеках, установите их администратором: `.venv/bin/python -m playwright install-deps chromium`. Скрипт сам не выполняет `sudo` и не останавливает ваши сервисы. Перед обучением освободите память от ненужных inference-серверов самостоятельно.

Если GitHub на Spark недоступен, склонируйте проект и MiniWoB на другой машине и перенесите каталоги. Можно указать `MINIWOB_URL=file:///absolute/path/miniwob-plusplus/miniwob/html/miniwob/` или HTTP URL страниц. Обычного Hugging Face токена для публичной модели не требуется; ключи не зашиты в код.

После `/dashboard` откройте адрес из строки `Dashboard ready`. По умолчанию используется порт 7861; если он занят, выбирается следующий свободный до 7870. Порт 7860 может быть занят SPL-FT. Адрес выводится только после проверки готовности BULFM. Явный выбор: `/dashboard 7862`. Для доступа с личного компьютера:

```bash
ssh -L 7861:127.0.0.1:7861 userdgx1@SPARK_IP
```

Затем откройте `http://127.0.0.1:7861` на своём компьютере. Это дашборд в реальном времени на вашем Spark, без публикации в облаке.

Отдельный запуск сервера:

```bash
./start.sh dashboard --host 127.0.0.1 --port 7861
```

Показатели: reward, success rate, GRPO loss, время шага, action tokens/s, learning rate, grad norm, пиковая зарезервированная GPU-память, RAM, доля групп с одинаковыми наградами, доля некорректных действий, оценка на отложенных сидах. На Spark CPU/GPU используют общую память; GPU peak и RAM нельзя складывать как независимые объёмы. GRPO loss не обязан монотонно падать: качество оценивайте по held-out success rate.

## Команды

| Команда | Действие |
|---|---|
| `/train [CONFIG]` | Новое обучение в отдельном процессе |
| `/status [RUN_ID]` | Статус, фаза, шаг и последние метрики |
| `/logs RUN_ID` | Последние 50 строк лога |
| `/stop RUN_ID` | Остановить после текущего optimizer step с сохранением |
| `/resume RUN_ID` | Восстановить веса, optimizer и RNG из последней контрольной точки |
| `/eval RUN_ID` | Отдельная оценка сохранённого LoRA-адаптера |
| `/config [FILE]` | Показать проверенные настройки |
| `/dashboard [PORT]` | Запустить веб-дашборд |
| `/benchmark [CONFIG]` | Сравнить 1/4/8 сред с реальными роллаутами и backward |
| `/doctor` | Проверить зависимости, CUDA, bf16, Chromium и страницы |
| `/exit` | Закрыть интерфейс; обучение продолжится |

Те же команды работают без интерактивного интерфейса: `./start.sh train configs/spark.yaml`, `./start.sh status`. `--runs /absolute/path` перед командой меняет каталог запусков. Это интерфейс управления обучением, а не подключённый к LLM чат-агент.

## Эксперименты

| Конфигурация | Назначение |
|---|---|
| `configs/spark-smoke.yaml` | 2 optimizer step, группа 2, до 2 действий, проверка полного цикла |
| `configs/spark.yaml` | click-test, 100 шагов, группа 4, до 6 действий, LoRA rank 16 |
| `configs/spark-book-flight.yaml` | Последовательный book-flight, 300 шагов, до 20 действий, контекст 4096 |
| `configs/spark-parallel-smoke.yaml` | Проверка 4 браузеров, пакетной генерации и cached decoding на 2 шагах |
| `configs/spark-book-flight-parallel.yaml` | 4 среды / batch 4, GRPO-группа 4, 300 шагов, оценка на 8 эпизодах |
| `configs/spark-book-flight-parallel-8.yaml` | 8 сред / batch 8, GRPO-группа 8, остальные настройки как у parallel-4 |

Меняйте `task`, `steps`, `group_size`, `groups_per_step`, `episode_steps`, `context_tokens`, `completion_tokens`, `learning_rate`, `beta`, LoRA-параметры и частоту evaluation в YAML. Параметр `steps` — optimizer steps; `episode_steps` — действия внутри эпизода. Каждый шаг собирает `group_size × groups_per_step` эпизодов. Начальная задача намеренно простая; успешный click-test ещё не означает умение работать с произвольными сайтами.

По умолчанию LoRA использует LFM3-модули `q_proj, k_proj, v_proj, o_proj, in_proj, out_proj, w1, w2, w3`, как в официальном LFM3 GRPO notebook. Для полного fine-tuning задайте `lora: false`, `beta: 0`; расход памяти выше. Ручная `/eval` сейчас поддерживает LoRA; автоматическая оценка до/после работает и при полном обучении.

Генерация идёт через одну обучаемую модель Transformers; копии весов в браузерных процессах не создаются. `num_envs` задаёт количество CPU-браузеров, `generation_batch_size` — максимальный batch одновременных запросов, `generation_use_cache` — KV-cache при генерации. Новые параллельные конфиги включают cache; старые сохраняют прежние значения для совместимости. Eager attention оставлен для совместимости гибридных операторов и GB10. Нет vLLM, Modal или обязательного внешнего трекера.

## Параллельный запуск и измерение 1/4/8

В существующем интерфейсе сначала `/stop RUN_ID` для старого запуска и дождитесь `stopped`. Закройте интерфейс через `/exit`, затем обновите код:

```bash
git pull --ff-only
./start.sh
```

Новые зависимости не требуются. В интерфейсе:

```text
/train configs/spark-parallel-smoke.yaml
```

После проверки запустите один из основных конфигов, начиная с 4 сред:

```text
/train configs/spark-book-flight-parallel.yaml
```

Среды сбрасываются и выполняют действия в отдельных CPU-процессах через `multiprocessing spawn`. Это не копирует CUDA-контекст обучающего процесса. Модель получает пакет запросов активных сред; завершившиеся эпизоды освобождают слот. Результаты сохраняют порядок участников GRPO-группы. Браузерные действия одного batch могут выполняться, пока модель генерирует следующий batch.

Веса не обновляются до завершения сбора группы. После сбора идут backward и optimizer step; генерация следующей группы выполняется на текущих весах. Это синхронный on-policy GRPO: отдельного асинхронного actor с отстающими весами нет. В конце запуска/при ошибке пул закрывает браузерные процессы; ошибка среды не подменяется нулевой наградой.

Оценка также работает параллельно, не вычисляет ненужные old/reference log-probabilities и пишет прогресс после каждого batch в лог и дашборд. В `state.json` доступны `eval_completed`, `eval_total`, `active_envs`, `generation_batch`, `last_response`, `valid_action`. Traces оценки помечены `evaluation: true`; незавершённая оценка не считается полной baseline при resume.

Для сравнения ресурсов остановите другие GPU-задачи и в обычном терминале выполните:

```bash
./start.sh benchmark configs/spark-book-flight-parallel.yaml
```

Одна загруженная LFM3 последовательно проверяет 1, 4 и 8 сред на 8 эпизодах, выполняет backward/optimizer и восстанавливает начальные LoRA-веса перед каждой проверкой. Отчёт `runs/benchmarks/TIMESTAMP/report.json` содержит время роллаутов/backward, episodes/min, tokens/s и пик памяти. Внутри интерфейса доступна та же команда `/benchmark CONFIG` (она занимает терминал до завершения).

Это короткий ресурсный тест: до 3 действий на эпизод и до 64 новых токенов. Он не оценивает качество и не гарантирует память для максимального контекста длинного обучения. Выбирайте число сред по измеренному `cycle_seconds` и проверяйте память на обычном train step. Ускорение на конкретном Spark нужно измерить: 8 сред могут оказаться медленнее 4.


## Как устроено обучение

Основа — [Liquid4All browser-control](https://github.com/Liquid4All/cookbook/tree/3d0cbcb7dc40b690e3e4996c5b78e4d3020f8232/examples/browser-control) и [официальный LFM3 GRPO notebook](https://github.com/Liquid4All/cookbook/blob/3d0cbcb7dc40b690e3e4996c5b78e4d3020f8232/finetuning/notebooks/lfm3_grpo_with_trl.ipynb). Реализация здесь самостоятельная: сохраняет задачу и алгоритм, но не является побитовой копией эксперимента.

1. BrowserGym локально запускает MiniWoB в headless Chromium. Вместо OpenEnv HTTP-сервера используется прямой Python API той же среды.
2. Все эпизоды одной GRPO-группы получают один seed состояния среды. Разные группы получают разные seeds.
3. LFM3 видит цель, предыдущие действия, ошибку и актуальный accessibility tree. Контекст ограничивается по токенам, сохраняя системную инструкцию и цель.
4. Веса фиксированы на время сбора группы; модель сэмплирует действия с temperature=1, без top-k/top-p отсечения. Награда — сумма фактических наград среды за эпизод.
5. Advantage — `(R - mean(group)) / (std(group) + 1e-4)`. Используется clipped GRPO surrogate с сохранёнными old log probabilities и опциональным KL к исходной модели через отключение LoRA. Нормировка — среднее по action-токенам эпизода, затем по группе. Один on-policy проход на optimizer step.
6. Каждый ход хранит собственные prompt/action tokens. Градиент идёт только по action-токенам; наблюдения среды не склеиваются в искусственное completion. Нет critic-модели.
7. Evaluation использует greedy actions и неизменные seeds из другого диапазона до/после и с заданным интервалом. Метрики success/reward сохраняются отдельно от train.

Группы с одинаковой наградой дают нулевой policy advantage. Если `zero_variance_groups` постоянно 100%, задача может быть уже решена либо слишком сложна для случайного исследования; увеличьте группу или смените задачу. Выходы с неправильным синтаксисом превращаются в `noop()` и сохраняются в traces; инфраструктурные ошибки завершают запуск с явным `failed`, а не маскируются под нулевую награду.

## Формат действий LFM3

Принимается один завершённый Python-вызов (`fill('19', 'OOK')`) либо один родной вызов LFM3 (`<tool_call><function=fill><parameter=bid>19</parameter><parameter=text>OOK</parameter></function></tool_call>`). Родной вызов преобразуется в тот же BrowserGym action. Поддерживаются click, fill, press, select_option, scroll и noop. Если ответ содержит рассуждение, выполняется только завершённый вызов после `</think>`. Незавершённые, неизвестные, дублированные или множественные вызовы отклоняются.

Лимиты можно менять в YAML: `context_tokens` ограничивает общий контекст, `completion_tokens` — новый ответ. Для длинных рассуждений разумный проверочный профиль — 8192/1024 вместо короткого smoke-бюджета. Изменения читаются при новом запуске. Увеличение лимита устраняет обрыв, а поддержка родного формата позволяет исполнить завершившийся tool call; это разные проверки. В traces сохраняется исходный ответ модели.

## Файлы запуска и восстановление

```text
runs/RUN_ID/
  config.yaml                 зафиксированные настройки
  runtime.json                версии, GPU, trainable params, resolved model commit
  state.json                  статус и прогресс
  worker.log                  stdout/stderr
  metrics.jsonl               train/eval события
  episodes.jsonl              train/eval наблюдения, ответы, действия и награды
  evaluation-before.json      held-out baseline
  evaluation-after.json       held-out after
  latest.json                 последняя полностью сохранённая контрольная точка
  checkpoints/step-000010/     модель/LoRA, tokenizer, optimizer и RNG
```

Сохранение идёт через временный каталог с атомарным переключением `latest.json`. Хранятся последние 2 точки по умолчанию. `/resume` берёт настройки запуска и последнюю целую точку, восстанавливает optimizer/RNG и продолжает со следующего шага. После аварийного завершения работа с последней точки может повториться; точное побитовое совпадение GPU/браузера не гарантируется. После перезагрузки Spark повторно запустите терминал и `/resume RUN_ID`.

Не запускайте два обучения одновременно на одном Spark без оценки памяти. На один RUN_ID действует файловая блокировка. `/stop` проверяется между раундами генерации и optimizer steps. Незавершённая группа отбрасывается, сохраняется последняя завершённая итерация; текущую генерацию и браузерный шаг нужно дождаться. Принудительный kill оставляет только ранее сохранённые точки.

Если Transformers сообщает `Could not import module AutoModel`, смотрите строку `Root cause` в дашборде или полный traceback в `worker.log`. Для ошибки `OpenSSL ... GEN_EMAIL` установка теперь явно включает совместимый `pyOpenSSL` внутри `.venv`: обновите репозиторий и повторите `bash scripts/setup_spark.sh`. Установщик и `/doctor` проверяют реальный импорт Transformers/PEFT, а не только наличие пакетов. После исправления ошибки до первого checkpoint начните новый `/train`.

## Curriculum на DGX Spark

Готовый пресет `configs/spark-curriculum.yaml` обучает одну общую LoRA на задачах
`click-test` / `click-button` → `enter-text` → `choose-date-easy` → `choose-date` → `book-flight`.
Восемь попыток внутри каждой GRPO-группы решают одну задачу с одним сидом; между группами
выбирается задача. Награды разных задач не нормализуются вместе.

```bash
cd ~/work/bulfm
git pull --ff-only
bash scripts/setup_spark.sh
./start.sh
```

В терминале BULFM:

```text
/train configs/spark-curriculum.yaml
/dashboard
```

Старый worker сначала остановите `/stop RUN_ID` и дождитесь `stopped` в `/status RUN_ID`.
Новый `/train` создаёт новый запуск от исходной модели; старые запуски сохраняются.
Для продолжения уже созданного curriculum используйте `/resume ЕГО_RUN_ID`.
Изменения пресета не применяются к работающему процессу или сохранённому конфигу старого запуска.

В пресете 8 браузеров, GPU batch 4, контекст 8192, ответ до 1024 токенов.
GPU batch уменьшен относительно batch 8 для снижения пиков памяти; точный расход зависит от длин ответов.
Начальная оценка выключена (`baseline_eval: false`), поэтому сразу собирается обучающая группа.
Это ускоряет начало, но исходного baseline в этом запуске нет. Для измерения улучшения включите
`baseline_eval: true` до запуска. Оценка проводится каждые 25 шагов по двум фиксированным
held-out сидам на каждую открытую задачу; это быстрая диагностика, а не точная оценка качества.
Число можно увеличить через `curriculum.eval_episodes_per_task`.

Переход к следующему этапу требует для **каждой** задачи текущего этапа минимум 16 обучающих
эпизодов, успеха ≥60% и среднего по эпизодам процента корректных вызовов ≥80% в окне последних
32 эпизодов этой задачи. Проверка выполняется после optimizer step. На верхнем открытом этапе
выбираются 70% групп, на предыдущих — 30%; задачи со смешанными исходами получают больший вес,
но полностью проваленные задачи тоже продолжают пробоваться. Автоматического перехода по таймеру нет.
Параметры изменяются в YAML (`promote_success`, `promote_valid`, `min_episodes`, `window_episodes`,
`replay_fraction`, `stages`). Состояние этапов восстанавливается из событий до загруженного checkpoint;
checkpoint сохраняется каждый шаг, хранятся последние два.

Дашборд показывает этап и таблицу успеха/корректности отдельно по задачам. В traces добавлены `task`
и `phase`; в `metrics.jsonl` — `task_stats`, `curriculum`, `learning_signal`.
`no_reward_variation` означает отсутствие GRPO-сигнала от награды на последнем шаге:
все попытки каждой группы получили одинаковую награду. Маленький KL loss этого не исправляет.
Корректный вызов (`valid`) может завершиться ошибкой страницы — она отдельно записана в `error`.
В наблюдении теперь сохранён `readonly`, поэтому календарь можно отличить от поля для ввода.
Никаких автоматических заполнений readonly-полей или дополнительных наград за синтаксис нет.

Если этап долго имеет 0% успеха и 100% zero variance, curriculum сам по себе не гарантирует
выход из этого состояния: потребуются демонстрации/SFT или более промежуточные задачи.
SFT-разогрев в этом изменении не реализован. Качество предобученной LFM3 нужно проверить на Spark.

## Проверка календаря на существующем checkpoint

Если обучение остановилось на `choose-date-easy` с почти одними `noop()`, сначала остановите
worker и дождитесь `stopped`. Readonly запрещает ввод, но не клик: календарь открывается кликом
по самому полю. Новая системная инструкция явно объясняет это без подсказки конкретной даты/ID.

```bash
./start.sh calendar-check RUN_ID
```

Также доступно `/calendar-check RUN_ID` в терминале BULFM. Проверка работает в foreground:
дождитесь завершения и не закрывайте этот терминал. По умолчанию сравниваются две даты,
для четырёх используйте `./start.sh calendar-check RUN_ID 4`.
Загружается последний сохранённый LoRA checkpoint, а не исходный адаптер. Один раз загруженная
модель проходит original/repaired варианты на одинаковых held-out сидах, greedy и без backward.
Сохраняются доли успеха, корректных вызовов и ошибок исполнения, время и полные traces в
`runs/checks/TIMESTAMP/`. Старые веса, optimizer, RNG-файл, state и конфиг не меняются.
Это небольшая диагностика инструкции, не доказательство статистически значимого улучшения.

Если уточнение даёт успешные прохождения и заметно больше корректных действий, примените его
и продолжите **тот же** запуск:

```bash
./start.sh calendar-fix RUN_ID
./start.sh resume RUN_ID
```

`calendar-fix` меняет только `system_prompt` в `runs/RUN_ID/config.yaml`, предварительно сохраняя
`config.before-readonly-fix-*.yaml`. Повторное применение не дублирует инструкцию.
Optimizer, веса, checkpoint step и история curriculum сохраняются. Поэтому старые неуспешные
эпизоды будут постепенно вытесняться из окна новыми; смена prompt сама по себе не означает рост качества весов.
Если сначала применили fix, последующий check всё равно берёт original prompt из резервной копии.
Активный worker и одновременный check/fix защищены проверкой PID и lock.

Если после уточнения всё ещё почти одни невалидные ответы/нет успехов, не расходуйте сотни
RL-шагов вслепую: изучите `episodes.jsonl` из проверки; следующим отдельным этапом нужен
SFT на демонстрациях или изменение формата инструментов. Эта команда не запускает SFT автоматически.


### Родной протокол LFM3

`native_tools: true` передаёт JSON-схемы через `tools=` и историю `assistant.tool_calls` / `tool`
в официальный chat template. Реальные ответы/ошибки среды сохраняются; невалидный ответ получает
сообщение об ошибке без выдуманного tool call. При нехватке контекста удаляются целые старые пары.
Текстовые инструкции старого стандартного prompt о Python-вызовах заменяются инструкцией вызова tools.
В наблюдениях убраны `readonly=False` и противоречивое `editable` у readonly-полей.
`enable_thinking=False` сохранён; абсолютного запрета рассуждений он не гарантирует.

Пресет curriculum включает родной протокол. Существующие конфиги остаются в legacy-режиме,
пока не выполнен `calendar-fix`. Теперь `calendar-check` сравнивает сохранённую обвязку с родным
протоколом и уточнением readonly, без обучения. Метрики `repaired` включают `native_tools: true`.
После проверки примените `calendar-fix` и `/resume`, если появились успешные прохождения.
Исходный checkpoint и optimizer сохраняются; улучшение формата ещё не означает улучшение весов.
